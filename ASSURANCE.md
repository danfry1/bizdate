# Assurance

What is actually verified about this package, by what method, and what those methods do not
cover. Written for someone deciding whether to depend on it for work that matters.

## Reference testing

Every calendar, convention, adjustment, schedule and accrual is compared against
**QuantLib 1.43**, the reference implementation this industry has checked its own systems
against for twenty years. The fixtures are generated by `scripts/generate-golden.py` and
record the QuantLib version, which the tests assert, so a regeneration against a different
version is a deliberate act rather than a silent change of reference.

| What | Cases |
| --- | --- |
| Holiday calendars | every holiday on 8 calendars, 1971-2100 |
| Day count conventions | 4,654 date pairs × 10 conventions |
| ACT/ACT ICMA | 14 coupon periods including stubs and month ends |
| BUS/252 | 665 pairs on two calendars |
| Business-day conventions | 7 conventions × ~3,900 dates × 4 calendars |
| Schedule generation | 1,144 schedules, date for date |
| Accrued interest | 1,375 bond coupons: period, day count and amount |

Two divergences from QuantLib are deliberate, listed in `tests/golden-holidays.test.ts` with
their reasons; anything else that diverges fails the suite.

## Property-based testing

`fast-check` pins the invariants that must hold for every input, not just the ones a test
author thought of: day count fractions are antisymmetric and never negative over a forward
period; an allocation always sums to the original total; an amortization always ends at a
zero balance with the principal repaid exactly; rounding never moves a value by a whole
minor unit; adding and subtracting business days round-trips.

Seeds are random per run, so the suite explores new inputs over time. Two defects in this
package were found that way.

## Mutation testing

Line coverage says code ran; it does not say a test would fail if the code were wrong.
Stryker changes the code deliberately — flips comparisons, inverts conditions, alters
arithmetic — and reports how many of those changes the suite catches.

**Score: 84.56% (86.79% of covered code), 2,019 of 2,361 mutants killed.**

Reproduce with `bun run test:mutation`; it takes about six minutes.

The 312 survivors were reviewed rather than waved away. They fall into four groups:

1. **Message wording (149).** Every mutation of a string literal in an error message or a
   holiday rule name that does not change a date. Error messages are deliberately not part
   of the API — the `code` and the structured fields are, and those are asserted. Holiday
   *names* are pinned for a full year on every calendar in `tests/holiday-names.test.ts`;
   what survives here is naming inside rules that produce identical dates.
2. **Equivalent mutants.** Changes that cannot alter any result: sign handling inside the
   greatest-common-divisor loops, which only ever see positive denominators; the
   uniform-rate fast path in `amortize`, whose slow path computes the identical payment;
   `raiseFraction`'s zero-exponent shortcut, which agrees with the general case; the memo
   check in `easterSunday`; and the headroom in `toNumber`'s scale, which is deliberately
   larger than a double needs.
3. **Unreachable guards.** Defensive checks on states the type system already rules out.
   Where these could be removed without weakening the code, they were: `accruedInterest`
   now has one testable guard instead of four untestable branches.
4. **Genuine gaps, now closed.** The first run scored 79.01%. Closing the real gaps it
   exposed — boundary conditions on both sides, guard clauses tested from one direction,
   joint calendars with differing weekends — raised it to 84.56% and **found two defects
   that the reference and property tests had both missed**: a percentage rate with
   surrounding whitespace (`' 2.5% '`) was rejected as malformed, and a `null` rate escaped
   as a bare `TypeError` instead of a typed error. Both are fixed, both have regression
   tests.

CI fails below 80%, so the score cannot quietly rot.

## Packaging and supply chain

- The whole suite is re-run against the built artifact, so a packaging or bundling defect
  cannot pass unnoticed.
- The packed tarball is installed and executed on Node 20, 22 and 24, as ESM and as
  CommonJS, and under Bun.
- Type resolution is verified with `are-the-types-wrong` for node10, node16 (both module
  systems) and bundler resolution.
- Zero runtime dependencies. Development dependencies are exact-pinned and enforced by
  `syncpack`; installs are frozen; lifecycle scripts do not run on install; a seven-day
  minimum release age applies to new versions.
- Releases publish from CI through OIDC trusted publishing with provenance attached, staged
  behind a 2FA approval, with a CycloneDX SBOM attached to the GitHub release.
- CodeQL and OpenSSF Scorecard run on every push.
- The suite runs under five exotic time zones on every CI run, so no result can depend on
  where it was computed.

## What none of this covers

- **Early closes.** These calendars answer whether a market is open, not what time it shuts.
- **Closures nobody has announced yet.** A new one ships in a patch release; a schedule
  built today cannot know about it.
- **Years outside each calendar's validated window**, which throw rather than guess.
- **Numerical claims beyond the stated conventions.** This package computes what the
  conventions say. Whether a given instrument uses a given convention is your term sheet's
  business, not this library's.
